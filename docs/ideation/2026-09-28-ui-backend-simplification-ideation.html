Ideation: UI and Backend Simplification

date
2026-09-28
topic
ui-backend-simplification
mode
repo-grounded
focus
Top-to-bottom review for simplification; the Applications and People views do not show what action is needed next; what can CRMs teach the UI model?

The app has one follow-up model on the server and three places in the UI where you have to go looking for it. Most of the complexity found here comes from that split. The survivors below mostly converge on one move: make "what do I owe, and when" the primary object, and let the pipeline and the people list sit behind it.

Reopens a prior decision

The 2026-09-08 People view requirements settled D2, "people only, not a mixed queue". Ideas 1 and 2 reverse that on purpose. The server already treats contact and application follow-ups as one model (server/lib/followup.js). Only the UI keeps them apart.

Grounding Context

Codebase Context

  • Shape. Vue 3 SPA with all state in App.vue (792 lines) and no store. Express + SQLite backend. An MCP server (server/mcp.js, 1812 lines, 28 tools) shares the services layer. Scale is about 76 applications, 115 leads and 10-30 contacts. Every account has one user, with an admin read-only view across users.
  • Three places to find the next action. Board cards carry one "signal" slot (client/src/utils/cardSignal.js). It shows a follow-up date if one exists, otherwise a staleness guess from updated_at. The People section groups contacts Overdue / Today / Upcoming / No commitment (contactGroups.js). Timeline is a third lens. No single view answers "what do I do today".
  • The follow-up model is asymmetric. Contacts carry next_action_at and next_action text (server/db.js:275). Applications carry only the date (server/db.js:195). An application can say when something is owed but not what.
  • Leads fill the board. The board builds its columns from legacy status (KanbanBoard.vue:305-311) and never reads record_type, so the 115 leads all land in Interested alongside real work.
  • The status split is half-finished. stage/state/close_reason/record_type are authoritative, but every write still also writes status. Queries COALESCE back to status for rows the backfill has not reached (services/applications.js:235-269). The backfill still runs in report mode, and the client still keys the board on status.
  • Sync machinery. A five-tier freshness state machine (utils/freshness.js, 289 lines), FreshnessBar + FreshnessSlot, a refetch queue gated on drag, a just-now hold, and day-rollover refetches handle applications. Contacts are left off the event stream (KTD8) and instead refresh from six hand-wired triggers in App.vue. A 2026-08-10 solution doc records a bug in which the tier ladder was never reached in the most common real failure.
  • History lives in three streams. Stage notes, contact interactions and the agent audit log. The record panel (ApplicationPanel.vue, 1651 lines) shows them in separate sections: Notes, Linked contacts, Activity.
  • Constraints carried in. AGENTS.md bans hero metrics. The 2026-08-16 ideation found that personal CRMs are usually dropped once upkeep becomes a chore, and that patterns built for large contact lists are anti-patterns at this size. Follow-up classification must stay server-side.

External context (prior art, from known product patterns)

  • Pipedrive, activity-based selling. Every open deal should have a scheduled next activity. A deal without one gets a warning, and marking an activity done prompts you to schedule the next.
  • Close CRM Inbox / HubSpot task queues. The home screen is a queue of owed actions (calls, emails, tasks) across every record, worked top-down. The pipeline is where you review. The queue is where you work.
  • Salesforce / HubSpot Leads vs Deals. Unqualified prospects live in a separate lead list and only enter the pipeline once they are qualified.
  • Help desks (Zendesk "Pending", Front "Waiting"). A ticket's state records whose move it is. Tickets waiting on the customer drop out of your work queue until they reply or a timer fires.
  • CRM record pages. One chronological activity timeline per record, with notes, emails, calls and system events interleaved. Associations to people and companies sit in a sidebar.

Topic Axes

  1. Next-action surface: what you see when you open the app
  2. Record and pipeline model: what a record is, and what "open" means
  3. Activity and history: how interactions are logged and read back
  4. Client state and sync: how the browser stays current
  5. Server layering and legacy: services, schema, migrations

Ranked Ideas

  • 2. Every open record has a next step: what, when, whose move

1

A Today queue as the home screen

Next-action surfaceConfidence 80%Complexity Medium
Description
Replace the Applications/People section toggle with a default Today view. It is one list of everything owed, from applications and people together, grouped Overdue / Today / This week, and each row states the action in prose ("Chase Acme recruiter about the panel date"). Pipeline (the board) and People (a plain directory) stay as secondary views you go to for review or lookup. Timeline either folds into the pipeline view or goes. The rows reuse the People view's existing snooze interaction.
Basis
direct: the server already has one follow-up model for both entities. AGENTS.md: "One follow-up model, shared ... Contacts and applications both consume it; neither adds a second". MCP already does "the morning sweep" as one list_applications call with follow_up_state: ["overdue","due"]. external: the Close CRM Inbox and HubSpot task queue pattern, where you work from the queue and review in the pipeline.
Rationale
You said the current views are poor for working out what to do next. That is structural: the answer is split across card signal slots, a separate People section and a Timeline, so you have to assemble it yourself. The server already computes the answer, and this view just shows it in one place. It also removes a top-level concept (section vs lens) from App.vue.
Downsides
Reverses D2 of the 2026-09-08 requirements. It needs a list endpoint that merges both entities, or the client merging two server-ordered lists, which risks the client re-sorting that KTD1 forbids. A merged server endpoint is the cleaner route. An empty queue has to feel like progress and not like nothing is happening.
2

Every open record has a next step: what, when, whose move

Record and pipeline modelConfidence 75%Complexity Low-Medium
Description
Add next_action text to applications so they match contacts. Then treat "open record with no next step" as the one condition worth surfacing, instead of the updated_at staleness guess on board cards. A next step can be my move ("send the take-home by Fri") or their move ("waiting on the recruiter; chase if nothing by the 3rd"). A their-move step stays out of the Today queue until its chase date. The card's signal slot then has exactly two things to show: the next step, or "no next step".
Basis
direct: server/db.js:275 adds next_action to contacts. Applications get only next_action_at (server/db.js:195). cardSignal.js falls back to stalenessSignal, which guesses from updated_at and legacy status. AGENTS.md notes that a date-only write does not bump updated_at, so the guess and the real commitment can disagree. external: the Pipedrive rule that every open deal has a scheduled activity, and help-desk "pending" state for waiting on the other side.
Rationale
Most of a job search is waiting. A Kanban stage says how far something got, but not whose move it is, and that is the question behind "what action is needed next". One small schema addition turns the card, the queue and MCP into answers to the same question, and deletes a heuristic.
Downsides
The documented risk is abandonment when upkeep becomes a chore. A required next step on every record could become exactly that chore. Keep it a prompt, not a gate (see idea 3), and let "no next step" be a quiet state rather than an alarm. "Whose move" can be modelled as the wording of the step and not a new enum. Decide that in the brainstorm.
3

Done asks "what next?"

Activity and historyConfidence 70%Complexity Low
Description
Marking a queue row done opens one small inline prompt: a note field (optional) and the next step with quick dates (+3d, +1w, pick). Skipping is allowed. Logging the interaction and re-committing become one gesture, from the queue, the record page or the board.
Basis
direct: the backend already made this one call. Commit e829d69 is "let add_note set the follow-up date, and unify the two writers", and AGENTS.md says of add_contact_note that "the moment you log a call is the moment you know when to chase next". The browser UI does not use it: contact snooze goes through updateContact, and application notes and follow-up dates are edited in separate panel sections. external: Pipedrive and HubSpot prompt for a follow-up activity when one is completed.
Rationale
This is what keeps idea 2 cheap to maintain. Next steps stay current because recording what happened asks for the next one, with no separate upkeep pass. It targets the abandonment risk directly.
Downsides
A prompt on every completion can feel like nagging. It needs a one-key dismiss, and "no next step" has to be a legitimate outcome, for example when the record should close.
4

Leads leave the board

Record and pipeline modelConfidence 75%Complexity Low
Description
Show only record_type = 'application' on the pipeline board. Leads go to a plain triage list sorted by date added, with two actions per row: Apply (promote) or Pass (close as not_pursued). The board's first column becomes a real stage, not a backlog.
Basis
direct: KanbanBoard.vue:305-311 builds columns from a.status and never reads record_type. With 115 leads and 76 applications, most of what the board shows is leads, all in Interested. App.vue already says leads distort the pipeline: "counting them as pipeline is what made every conversion rate wrong". external: the Salesforce/HubSpot split between leads and deals.
Rationale
The board becomes readable at a glance, which is the stated design goal ("forward motion is the hero"). The data model already makes this distinction, so this is mostly a filter plus a small list view.
Downsides
Adds a view, although it is simpler than the column it replaces. Leads you intend to apply to soon need a way to show up in Today. A next step on a lead (idea 2) covers that.
5

Finish the status split

Server layering and legacyConfidence 85%Complexity Medium
Description
Run SCHEMA_BACKFILL=apply in production, then remove the COALESCE(..., status) fallbacks. Move the board and cardSignal onto stage/state, and stop dual-writing status: make it a read-only derived field in responses for MCP compatibility, or drop it with a version note. Fold the two ServiceError classes into one while touching this.
Basis
direct: services/applications.js:235-269 has three COALESCE fallbacks "for rows the backfill has not reached". AGENTS.md: "The status split backfill runs on startup in report mode and writes nothing". The client board keys on status although AGENTS.md says "never [filter] on status". mcp.js toolError checks two ServiceError classes because "The contacts service defines its own".
Rationale
Two sources of truth for one fact cost something on every write path and in every query, and the migration is mostly done. It is also the prerequisite that makes ideas 2 and 4 clean, because both key on state and record_type.
Downsides
Touches production data. It needs a backup and a report-mode dry run you have reviewed first. External MCP clients that read status may break if it is dropped rather than derived.
6

One sync path, two freshness states

Client state and syncConfidence 65%Complexity Medium
Description
Move record data out of App.vue into one small store composable with a single invalidate(entity, id?). Put contacts on the existing change stream, so the six hand-wired contact refresh triggers and the separate applications refetch queue collapse into one path. Reduce the five-tier freshness ladder to two states: live, or not live, with a Reload.
Basis
direct: App.vue: "Six triggers can call this, so it carries the same discipline the applications refetch already has". It keeps separate sequence tokens, scope checks, a drag-gated refetch queue, a just-now hold, and a day-rollover refetch. Contacts are excluded from the stream ("not on the change event stream (KTD8)"). freshness.js is 289 lines for tiers pending/live/degraded/stale/terminal. The 2026-08-10 solution doc records that "the entire tier ladder ... was unreachable in the most common real failure". reasoned: this is a mostly single-user app with a few hundred rows. The stream exists so that MCP agent writes appear, and a second-by-second degrade/stale distinction gives that user little they can act on.
Rationale
This is where most of the incidental complexity in App.vue sits, and it grows each time an entity is added (contacts already needed a parallel copy). A single store also gives the Today queue (idea 1) one place to read merged data from.
Downsides
The freshness tiers came from a deliberate plan (2026-08-08), and some of their accessibility wording is careful work. Collapsing them discards it. The drag-safety gate is still needed while the board supports drag.
7

The record page is one activity timeline

Activity and historyConfidence 60%Complexity Medium-High
Description
Reshape the 1651-line ApplicationPanel around a CRM record layout. At the top: the next step, with Done/Snooze. Below it: one chronological feed that merges stage notes, interactions with linked people, stage changes and agent actions. Details, JD, documents and attachments move to secondary tabs. On the backend, consider one notes table keyed by subject (application or contact) in place of stage_notes + contact_notes. They already share the hide-not-delete, updated_at and hidden_at semantics.
Basis
direct: the panel outline shows separate Notes (ApplicationPanel.vue:86), Linked contacts (:407), Activity/audit (:668) and Dates grid (:456) sections. AGENTS.md describes the two note tables with the same hide semantics and two different edit shapes (update_note replaces while update_contact_note patches), which "will bite an agent that assumes they do". external: HubSpot/Salesforce record pages with a single activity timeline.
Rationale
Opening a record to decide what to do next currently means reading three sections and reconstructing the order yourself. One feed answers "what happened last", and the next step sits directly above it. A merged notes table would also remove the two tool shapes that differ for no domain reason.
Downsides
The largest change here. The table merge is a real migration with backup and MCP compatibility concerns, and could be deferred while the UI feed ships first as a read-side merge. Ranked last because ideas 1-3 capture most of the value of "what next" without it.

Rejection Summary

30 raw candidates were generated across six lenses. Ten merged into the survivors above and 13 were cut. Critique was done in this session, not by a separate fresh-context verifier, so the verdicts below have not been independently checked.
