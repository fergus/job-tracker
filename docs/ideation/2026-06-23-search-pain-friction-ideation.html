Grounding Context

Codebase Context

  • Vue 3 + Express 5, SQLite WAL, Docker single-image, oauth2-proxy auth
  • Self-hosted multi-user — technical audience
  • 3 views: Kanban (default), Table, Timeline
  • MCP server (port 3001, 14 tools) for AI agent access
  • Design personality: "tactical, forward, sharp — mission board meets editorial spread"

Current Search State

  • No text search exists anywhere in the app
  • Only filters: showClosed toggle (client-side), updated_since, company_name LIKE
  • Client loads full dataset (max 200); filters via computed properties
  • MCP list_applications: same narrow filter surface as REST API
  • extracted_text on attachments, extracted_jd on applications — stored, never queried

Past Learnings (Constraints)

  • Double-array-scan risk: multiple computed properties independently scanning applications array caused perf issues — use a single combined pass
  • dragActive guard: filter changes during drag break Sortable.js drop zones
  • Panel close: close ApplicationPanel synchronously when filter removes panel's app from visible set

External Research

  • MiniSearch: best client-side lib for small datasets; field boosting, fuzzy matching
  • SQLite FTS5: viable with better-sqlite3; BM25 scoring; snippet() highlights
  • Filter chip pattern (Linear/Jira): dismissible chips for active filters
  • JobSync (closest analog, 625 stars): no documented search implemented

I-1

Attachment Text Search Dead End

query-scope Confidence: High Complexity: Low

Description

The system already extracts text from CVs, cover letters, and other attachments into extracted_text columns (attachments table) and extracted_jd on applications. That extracted text is piped to the AI generation context — but is completely absent from any search or filter. A user who wants to find "the application where I mentioned 'distributed systems' in my cover letter" has no path forward except opening each application individually. The richer and more tailored the user's documents are, the more painful this is. Stage notes (per-stage interview observations, recruiter call content) face the same blackhole: they are displayable and returned by get_application, but list_applications cannot search by their content.

Basis

direct: "extracted_text, extracted_at, generated_by, generation_task columns on attachments table" (evidence-query-scope.md:97) + "extracted_jd column" added at server/db.js:164-166 + "list_applications — Inputs: status (enum), company_name (string, partial match), updated_since (ISO 8601), fields (array), limit (int 1-200), offset (int >= 0)" (evidence-api-integration.md:8) — no full-text param present.

Why It Matters

Job seekers who tailor cover letters and CVs per application store the richest, most differentiated signal in the least accessible place. The data pipeline is already complete: upload → extract → store. The retrieval half of the loop was never built. Adding full-text search over extracted_text and stage_notes.content closes the loop without changing the schema.

Downsides

FTS5 virtual table requires a migration and sync triggers; client-side search (MiniSearch) can't reach the attachment text without first fetching it, making it server-side only for this field. Either way, attachment content is variable-length, making relevance ranking more important than simple substring matching.

Meeting Test

"We already extract the text for AI context — we're just not letting people search it."

I-2

Salary Range Stored, Salary Filter Missing

query-scope Confidence: High Complexity: Low

Description

Salary fields (salary_min, salary_max) were added via migration and are prominently displayed in the ApplicationPanel. A job seeker comparing offers, reviewing active pipeline, or deciding where to follow up can't ask "show me everything above $120k" or "which applications have no salary recorded." Every filter in the API is string or status-based — no numeric range comparisons exist. This is arguably the most actionable filter for actual job-search decisions, and it's entirely missing.

Basis

direct: "salary_min (94), salary_max (96)" migration columns at server/db.js:91-107 (evidence-query-scope.md:15) + "ApplicationPanel.vue:271-289 — salary_min, salary_max displayed in 2-column grid" (evidence-query-scope.md:89) + MCP list_applications inputs listed at evidence-api-integration.md:8 — no salary_min, salary_max, or salary range filter parameter present.

Why It Matters

Compensation is often the deciding filter in job search decisions. "Which companies offered 15% above my target?" is a real weekly question. The data is stored — the gap is purely in the query surface. Numeric range params (salary_min_gte, salary_max_lte) are a small API addition with disproportionate decision-support value.

Downsides

Salary data is inconsistently recorded — many applications won't have it. A filter for salary range with sparse data will often return an empty set, leading users to conclude the filter is broken. UI should communicate sparsity (e.g., "4 of 23 applications have salary data").

Meeting Test

"Salary data is the most actionable field in the tracker and we can't query it."

I-3

No Cmd+K Search Invocation

search-ux Confidence: High Complexity: Low

Description

There is no global search shortcut in the application. The keyboard event inventory is complete — Escape closes modals, Ctrl/Cmd+Enter submits notes, Enter/Space selects cards — and the dossier notes explicitly: "no global search shortcut (Ctrl+K, Cmd+K) exists." For a technical, self-hosted user base accustomed to Cmd+K in Linear, Notion, or GitHub, there is no muscle memory to exploit. A search feature without a keyboard invocation path is invisible: users will reach for Cmd+F (browser find), fail to find what they want, and conclude search doesn't exist — even after it's shipped.

Basis

direct: "Pattern: Enter/Space triggers select; no global search shortcut (Ctrl+K, Cmd+K) exists." — evidence-search-ux.md:218, confirmed by complete keyboard event survey at lines 174-218 covering all registered keydown handlers across App.vue, ApplicationPanel.vue, KanbanCard.vue, TimelineView.vue, SettingsPanel.vue.

Why It Matters

Discoverability determines adoption. This is as important as the search engine itself. A Cmd+K shortcut that focuses a search input and opens a command palette is the expected entry point for power users in this tool category — it is what makes search feel like a first-class feature rather than an afterthought buried in the toolbar.

Downsides

Cmd+K on macOS and Ctrl+K on Windows/Linux need to avoid collisions with browser shortcuts (neither is claimed by major browsers in app contexts). The shortcut must not fire when focus is inside a textarea or other text input — standard guard needed.

Meeting Test

"If we ship search without Cmd+K, technical users will never find it."

I-4

"Hide Closed" Toggle Loses Meaning at Scale

search-ux Confidence: High Complexity: Medium

Description

The showClosed toggle (App.vue:186-207) is a binary: all closed visible, or none visible. As the tracker accumulates months of history, the user's real need becomes finer-grained: "hide closed from more than 3 months ago" or "show only closed in the last 30 days to review what went wrong." A 100-application history with the toggle enabled is an unfiltered wall; with it disabled, complete blindness to recent outcomes. Critically, the codebase already distinguishes "recent closed" from "older closed" — KanbanBoard.vue:280-292 has isRecent() logic and an olderCards computed — but this distinction is never surfaced as a user control.

Basis

direct: "const showClosed = ref(storageGetBool(SHOW_CLOSED_KEY, true))" at App.vue:186 (evidence-search-ux.md:6) + "function toggleShowClosed() { if (dragActive.value) return; showClosed.value = !showClosed.value; }" at App.vue:203-207 + KanbanBoard.vue:280-292 isRecent / olderCards logic confirmed in evidence-state-interaction.md:173-198: the code already distinguishes "daysSinceClosed < RECENT_CLOSED_DAYS" but exposes no user control over the boundary.

Why It Matters

The most painful UX moment in a long job search is when the "Show closed" button becomes a firehose. The distinction between recent and older closed applications is already encoded in the render logic — this idea is about exposing what already exists internally as a user-facing control, not adding new logic.

Downsides

A three-way toggle (All / Recent 30d / Active only) replaces a binary — more cognitive weight. The dragActive guard must cover all three states. The panel-close watcher must be updated to fire for all non-"show all" modes, not just when showClosed becomes false.

Meeting Test

"We already split recent vs older closed in the Kanban column code — why isn't that a filter option?"

I-5

MCP list_applications Has No Text Search — AI Agents Are Equally Blind

api-integration Confidence: High Complexity: Medium

Description

The MCP list_applications tool supports the same narrow filters as the REST API: status enum, company_name LIKE, updated_since, and pagination. An AI agent asked "find me applications where the JD mentions Kubernetes" must call list_applications repeatedly with pagination, then call get_application for each record, then scan the text manually — up to 200 calls for a full corpus scan. There is no text-search parameter in any MCP tool. The app has MCP integration precisely to let AI agents work on the user's behalf; a search gap at the human level is a 200x amplified gap at the agent level.

Basis

direct: "list_applications — Inputs: status (enum), company_name (string, partial match), updated_since (ISO 8601), fields (array), limit (int 1-200), offset (int >= 0)" at mcp.js:102-201 (evidence-api-integration.md:8). No q, no search, no query, no text parameter. Default pagination limit 50, max 200, confirmed same file.

Why It Matters

Adding a q parameter to list_applications would make AI workflows dramatically more useful without changing the human UI at all. It's the highest-leverage API surface change: one parameter addition unlocks text retrieval for both human callers (REST) and agent callers (MCP) simultaneously. Agent use will grow as this tool matures — getting the query contract right now prevents schema churn later.

Downsides

A q parameter requires deciding what fields it searches (company_name + role_title only? or also notes and JD text?) and what implementation backs it (SQLite LIKE, FTS5, or client-side). The decision is entangled with idea #1 and #7 — consistent implementation approach across all three matters.

Meeting Test

"Our AI tools have to scan every record one by one to answer a text question — that's a real latency and cost problem."

I-6

Panel Auto-Close Logic Doesn't Cover Search Filter

state-interaction Confidence: High Complexity: Low

Description

The existing panel-close watcher (App.vue:216-224) closes the ApplicationPanel when showClosed changes and the panel's current application is now filtered out. That watcher is specific to the showClosed ref. When search filters are added, a user could type a query that removes the currently-open application from the visible set — and no watcher handles that case. The panel stays open showing an application that no longer appears in the board, creating a phantom context divergence: the user is editing a record they can't see in any list, with no visual affordance that the panel is "detached." This is the same failure mode documented in past learnings — it was solved for one trigger and will bite again with the second.

Basis

direct: "watch(showClosed, (visible) => { if (!visible && panelApp.value && TERMINAL_STAGES.includes(panelApp.value.status)) { showPanel.value = false; } })" at App.vue:216-224 (evidence-state-interaction.md:52-64). The watcher tests TERMINAL_STAGES membership, not whether the app is in the current filtered set — a search filter could hide any application regardless of status, which this watcher ignores.

Why It Matters

Past learnings document this exact pattern as a known failure mode. The fix is mechanical: a generalized "if panelApp is not in displayApplications, close synchronously" invariant that covers all filter triggers, not just showClosed. Calling this out before the implementation starts is what prevents it — the failure mode is silent (no error) and data-safe but creates a confusing UX state that is hard to reproduce and debug after the fact.

Downsides

A generalized panel-close watcher that fires on any displayApplications change must be carefully debounced if search is debounced — closing the panel mid-keystroke as intermediate query states exclude the current record would be jarring. The watcher should close only when the query is "settled," not on every keystroke.

Meeting Test

"We already solved this for showClosed — we need to make sure the search filter triggers the same panel-close logic."

I-7

Full Dataset Is Client-Side, But No Search Library Installed

technical-approach Confidence: High Complexity: Low

Description

The application loads the full application list client-side (App.vue:174) and performs all filtering via Vue computed properties. This is precisely the dataset profile for which MiniSearch was designed: small-to-medium in-memory collections (personal job tracker max: ~200-500 records) with field boosting and fuzzy matching. No search library is currently installed (confirmed: no MiniSearch, Fuse.js, or lunr in client dependencies). A MiniSearch index over company_name, role_title, job_location, and notes would run entirely in-browser, require no server changes, return results in under a millisecond, and handle the fuzzy company-name problem that SQL LIKE cannot (typing "Googel" still finds Google). The dataset is already in memory — no index sync, no server round-trip.

Basis

direct: "App.vue:174 — applications ref: raw array from API" + "Client-side filtering (no API query param for filtering by status)" (evidence-search-ux.md:103-113). external: MiniSearch — described in grounding as "best client-side library for small datasets; supports field boosting, fuzzy matching." Verifier confirmed no search library in client dependencies.

Why It Matters

Client-side search is the fastest path to shipping working search for company_name, role_title, and location — no schema migration, no server-side query changes, no FTS5 virtual table. It composes naturally with the existing computed property filtering architecture and can be wired into the same displayApplications pass. The limitation is scope: large text fields (JD text, extracted attachment content) should route to server-side FTS5, making the two approaches complementary rather than competing.

Downsides

Client-side search can't reach attachment text or JD content (stored in DB, not in the client-loaded record). The MiniSearch index must be rebuilt when the application list refreshes. Fuzzy matching at low thresholds may surface false positives — tuning the fuzzy tolerance is non-trivial for varied company name formats.

Meeting Test

"We already have every record in memory — adding MiniSearch would give us fuzzy search in an afternoon."

Rejection Summary

# Idea Reason Rejected
C-1 No "Stale Applications" Query Mode Correct but low novelty — covered by the query-scope gap; an updated_since inversion is a thin extension of existing API params, not a distinct direction worth standalone discussion at this ideation stage.
C-2 Location Field Stored as Freetext, Never Queryable Valid but lower-leverage — freetext location data is inconsistently entered ("remote", "Remote", "100% remote") and needs normalization before a location filter is reliably useful. Worth a sub-requirement under a broader filter expansion, not a primary idea.
C-3 No Compound Filter Composition Overstated: MCP already supports multi-param calls (status + company_name + updated_since can be combined today). The server WHERE clause already ANDs conditions. The real gap is missing filter types — covered by ideas I-1 and I-2 — not missing AND logic.
C-4 New Search Filter Risks Double-Scan Performance Bug Factually correct, fails the meeting-test at this app's scale. A personal job tracker with <500 records incurs no meaningful performance cost from a third array scan. Valid implementation footnote, not a standalone product idea.
C-5 dragActive Guard Doesn't Cover Search Input State Speculative — describes an interaction with a feature that doesn't exist yet. The failure mode (typing during drag changes column content) is an edge case that is unlikely in practice. Implementation caution note, not a product idea.
C-6 Per-Stage Notes Are Invisible to Any Query Basis refuted by verifier: stage_notes ARE joined in list_applications when includeNotes is true (services/applications.js:67-76). The real gap — searching by note content — is absorbed into idea I-1 (Attachment Text Search Dead End), which covers all rich-text search including notes.
C-7 Audit Log Exists but Cannot Be Queried for Pattern Detection Analytically interesting but scope-adjacent — aggregate funnel analytics ("time-to-response by company type") is a different product direction from search/find/filter. Worth its own ideation session, not a search feature.
