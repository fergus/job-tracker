June's ideation covered roles and their notes only. Since then the app gained people, contact notes, LinkedIn connections, Today, the stage/state/close-reason split and an agent-first pitch. This refresh re-grounds search against that app. It replaces the June ranking, which is kept in Prior Ranking (June 2026) for reference.

Grounding Context

Codebase Context

Stack
Vue 3 single-page app with no router, Express 5, SQLite in WAL mode via better-sqlite3, one Docker image behind oauth2-proxy. A separate MCP server (server/mcp.js) on its own port with Bearer API keys. A live-update stream via emitChange in server/lib/events.js.
Text that holds what a user would search for
  • applications: company, role title, job description, posting and company URLs, interview notes, prep work, extracted JD, location, next action (server/db.js:34-53 plus later migrations).
  • stage_notes.content and contact_notes.content, both soft-deleted via hidden_at.
  • attachments: filename, extracted_text (added later, db.js:141), generated_by and generation_task.
  • contacts: name, role, employer, email, phone, notes, next action, LinkedIn URL. Linked to roles through contact_links(contact_id, application_id, relation) (db.js:243-250).
  • connections (imported LinkedIn): names, company, position, email, URL, and a normalised company_key (db.js:323).
  • user_profiles: CV markdown, career narrative, target roles, agent instructions.
Search today
  • Roles: company_name LIKE only (server/services/applications.js:272-273). The June bug where the REST route dropped company_name is fixed.
  • People: name, employer or role LIKE, unescaped (server/services/contacts.js:213).
  • Connections: escaped LIKE over name, company and position; exact match on company_key (server/services/connections.js:240-249).
  • Nothing searches notes, job descriptions, interview notes, prep work, contact notes, attachment text or profile text. No FTS table exists.
  • MCP list_applications tells agents to "locate records by ID, then call get_application(id)" (server/mcp.js:122); its only text filter is a partial company name.
  • The client has no search input. People has a deliberate "no filter control" rule (client/src/components/PeopleView.vue:103). Today rows show only the next action or "Follow up" (TodayView.vue:104).
Constraints and learnings
  • emitChange is application-scoped. Its only callers are application routes and services, notes and MCP. Contact and connection writes do not emit.
  • Any index is derived state. Write to the database first, then reconcile on boot alongside the existing file sweeper (docs/solutions/logic-errors/file-cleanup-ordering...).
  • Filter changes must guard drag state and close the detail panel synchronously (docs/solutions/ui-bugs/showclosed-toggle-drag-guard...).
  • Product: "campaign tool, not a CRM"; "information density earns its keep"; the audience is self-hosters who run an MCP client. Nothing leaves the server unless the user connects an agent or sets OPENAI_API_KEY.
External context (moderate confidence, secondary sources)
  • Trackers like Huntr and Teal compete on capturing jobs, not on finding things in your own data. Monica CRM searches contacts and notes through a pluggable backend.
  • FTS5 trigram matching has a hole for queries under 3 characters. bm25 scores are not comparable across separate tables, so one denormalised search table is simpler.
  • Hybrid FTS plus sqlite-vec with reciprocal rank fusion (Simon Willison / Alex Garcia) is the usual local semantic pattern.
  • OpenAI's deep-research MCP convention is two tools, search and fetch. Anthropic's tool guidance favours concise responses, ids to expand, and actionable empty results.

Topic Axes

  1. What gets searched: which records and text fields are in scope, and how they relate.

  3. Finding it in the app: how a person searches in the UI.
  4. Surfacing without asking: records brought forward by context rather than a typed query.
  5. Index trust and plumbing: keeping results correct, fast, local and private.

1. One search index over every record, kept honest

Index trust and plumbingConfidence 85%Complexity MediumSupersedes June #1 and #3
Description
One self-contained FTS5 table, search_doc, holds a row per searchable thing: a role, a stage note, a contact, a contact note, a connection, an attachment's text, and profile text. Each row carries its type, id, parent role, state and timestamps. The index is fed by SQLite triggers rather than emitChange, because contact and connection writes never emit. Hidden notes are removed when they are hidden. A boot reconcile compares row counts with the source tables and rebuilds anything that drifted, next to the existing file sweeper. Queries under three characters fall back to a prefix or LIKE match so "AI" and "Go" still work. Results come back grouped by type with per-type limits, so a 3,000-row LinkedIn import cannot crowd out roles and notes. The first release should weight user-written notes above job descriptions and attachment text.
Basis
  • direct: search is a separate LIKE per table with different escaping. Roles: conditions.push("a.company_name LIKE ?"); (server/services/applications.js:273). Contacts: conditions.push("(name LIKE ? OR employer LIKE ? OR contact_role LIKE ?)"); (server/services/contacts.js:213). Connections escape % and _ (server/services/connections.js:244).
  • direct: emitChange(userEmail, type, applicationId) is called only from application routes and services, notes and MCP. That rules it out as the indexing hook for people and connections.
  • external: bm25 is not comparable across FTS tables; trigram returns nothing under 3 characters; one author found that external-content tables built from composed fields broke highlighting.
  • reasoned: the derived-state learning (database first, reconcile on boot) applies to any index.
Rationale
Every other idea here reads from this table. June stopped at roles and stage notes. People, contact notes and connections are now the largest volume of unsearched text, and one table avoids building three more per-entity search paths that would each drift.
Downsides
Triggers on seven tables plus a migration and a rebuild path. Attachment text arrives after the attachment row is created, so the index has to catch that update. Per-type limits make the result shape grouped rather than one ranked list, which the UI and the MCP contract both have to accept.

2. Search-then-fetch for agents, with a coverage receipt

Agent retrievalConfidence 85%Complexity MediumSupersedes June #2
Description
Two MCP tools replace "list, page, then fetch each record". search(q, types?, state?, limit, detail) returns typed handles (app:12, contact:4, note:88, conn:301) with a title, a short snippet and the field that matched. Counts per type come first so the agent can narrow before fetching. fetch(handle) returns the full record with its linked context. Every response carries a coverage block: how many of each type were searched, which attachments have no extracted text, and that hidden notes were excluded. An agent can then say "you never wrote about Kubernetes" with confidence, or "4 PDFs were not searchable", instead of treating an empty result as a fact.
Basis
  • direct: "Use this to locate records by ID, then call get_application(id) to fetch the full detail including job_description, extracted_jd, interview_notes, and prep_work." (server/mcp.js:122). The only text filter is company_name, "Filter by company name (partial match)" (server/mcp.js:130-133).
  • external: OpenAI's deep-research MCP convention (search returns ids and titles, fetch(id) returns text); Anthropic's tool guidance on concise responses and actionable empty results.
  • reasoned: agents act on absence ("no prior contact at Stripe, so draft a cold email"), so a wrong negative causes a real-world mistake.
Rationale
The README now pitches "a self-hosted job tracker your AI agent can work". Today an agent asked "who did I talk to about the Rust role?" has to page every role and contact and fetch each one. This is the most visible gap in that promise, and following the two-tool convention means research modes in generic MCP clients work without setup.
Downsides
Two more tools on an already large MCP surface, and the handle format becomes a public contract. Relevance ordering changes as data changes, which tests have to allow for. Without idea 1 the tool can only search names, so it ships after the index.

3. Related records on every role and person

Surfacing without askingConfidence 85%Complexity LowNew
Description
Opening a role shows the people linked to it, their latest notes, earlier roles at the same company with their close reason, and connections who work there. Opening a person shows their roles and recent notes. The same answer is available to agents as related(type, id), and as a possible_related field when an agent creates a role or contact, so it sees "you were rejected here in March" before it creates a duplicate. No query and no index are needed for the core of it.
Basis
  • direct: people are already joined to roles by id: CREATE TABLE IF NOT EXISTS contact_links (... contact_id ... application_id ... relation TEXT ...) (server/db.js:243-250).
  • direct: get_application_context (server/mcp.js:782) returns the role, notes, attachments and profile but not the linked people, so agents miss them today.
  • external: the related-records sidebar in sales CRMs and the contact panel in email clients.
Rationale
This is the cheapest way to show that search means more than a box. It uses the people data June could not, it catches the "I applied here two years ago" case, and it ships before the index exists.
Downsides
"Same company" for earlier roles and connections needs company matching, which is only clean once idea 5 lands. Until then it is limited to explicit links plus an exact company-name match. Adding the result to create responses changes the MCP contract.

4. Ctrl+K palette with record links and paste-to-open

Finding it in the appConfidence 75%Complexity MediumReverses June's deferral
Description
Ctrl/Cmd+K opens one palette grouped into Roles, People, Notes and Connections. When empty it lists recent records and what Today has due, so most uses need no typing. Pasting an email address, LinkedIn URL, posting URL or phone number does an exact lookup and opens that record directly. Every result has a hash link (#/app/12, #/contact/4), which gives records an address for the first time, so an agent can hand the user a link that opens the right panel.
Basis
  • direct: <!-- R2: one scroll, four groups, no filter control. (client/src/components/PeopleView.vue:103). People deliberately has no filter, so one palette fills the gap without adding filter bars to each view.
  • direct: the app already rewrites its URL with window.history.replaceState(null, "", url.pathname + url.search + url.hash); (client/src/App.vue:563), so hash links fit without a router.
  • direct: exact identifiers already exist as columns: connections url TEXT NOT NULL and email TEXT (server/db.js:320-321), and contact email and phone (server/db.js:227-228).
  • external: the command palette pattern (grouped by type, recents when empty) and caller-ID "screen pop" lookup in call centres.
Rationale
Board, Timeline, People and Today share no way to find anything. A keyboard palette suits the "tactical, sharp" brand and keeps views uncluttered. Recents and paste-to-open work before the index exists, so this can ship in two steps.
Downsides
Opening a record from the palette must follow the drag-guard and panel-close rules. Hash links add a small routing layer to maintain. The Notes group only becomes useful once idea 1 ships.

5. Who do I know at this company

What gets searchedConfidence 65%Complexity MediumNew
Description
Give roles and people the same normalised company key that connections already have, so a search for "Stripe" returns one grouped answer: the roles and leads, the people who work there, and the LinkedIn connections there. Show connections only for companies with an open role or lead, so a 3,000-row import becomes a referral finder rather than noise. This is deliberately narrower than a general company entity.
Basis
  • direct: connections normalise the company (company_key TEXT, at server/db.js:323) and filter on it exactly (where.push("company_key = ?"); at server/services/connections.js:240). Roles use free-text company_name LIKE (server/services/applications.js:273), and contacts store employer TEXT, (server/db.js:226). The three cannot be joined reliably today.
  • reasoned: a warm intro is the strongest move in a job search, and no tracker competitor has a connections table to answer this.
Rationale
This makes the LinkedIn import useful and powers idea 3's "connections there" and idea 6's context line. It is the main thing this app can answer that a spreadsheet or Huntr cannot.
Downsides
Needs a migration that backfills a key on roles and contacts and a decision on whether to reuse the connections normaliser. "Acme" and "Acme Holdings" will still miss without manual merges. The verifier judged a full authority file to be overreach; keep it to the key.

6. Today rows carry their context

Surfacing without askingConfidence 70%Complexity LowReshapes June's rejected push surface
Description
Each Today row gets one context line drawn from idea 3's join: the last note with that person, other open roles at the company, or "2 connections here". The follow-up itself is the query, so the user gets recall at the moment they reach out, without searching.
Basis
  • direct: Today rows currently show only item.next_action || 'Follow up', (client/src/components/TodayView.vue:104).
  • direct: Today is the daily surface agents mirror: "filter follow_up_state to ["overdue","due"] ... to match the Today screen" (server/mcp.js:122).
Rationale
Users check Today daily, so this is where retrieval gets seen most. It costs little once idea 3 exists.
Downsides
Keep it to one line. Rule-based nudges ("no note in 30 days") were considered and left out because they drift toward the CRM the product says it is not. Today rows become heavier to compute.

7. Let the agent bring the synonyms

Agent retrievalConfidence 60%Complexity LowReplaces local embeddings
Description
The MCP search tool accepts several phrasings (queries: ["backend", "server-side", "platform engineer"]), and its description asks the agent for two to four. The server runs each through the local index and merges them with reciprocal rank fusion. This gets most of the benefit of semantic search without shipping a model or sending data anywhere.
Basis
  • external: reciprocal rank fusion as used in hybrid SQLite search (Simon Willison / Alex Garcia). Embeddings at this scale mainly add synonym matching.
  • reasoned: the connected agent is already a strong query rewriter at no cost to the server, and docs/guide/data-flows.md promises nothing leaves the box unless the user opts in.
Rationale
It settles whether embeddings belong on the roadmap. For agent users the answer becomes no, and people using the UI keep plain FTS.
Downsides
Only helps agent searches. Depends on idea 1 and is a parameter of idea 2's tool, so it is a design decision rather than a release on its own.
