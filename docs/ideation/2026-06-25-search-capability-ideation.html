FTS5 Universal Search Layer

Description

Add a SQLite FTS5 virtual table (applications_fts) using an external content table so data is not duplicated. The FTS index covers company_name, job_title, notes, job_description, and extracted_jd from the applications table. A separate stage_notes_fts covers stage_notes.content. Triggers (INSERT / UPDATE / DELETE) on both source tables keep the indexes in sync. A single _migrations entry adds the virtual tables and triggers. BM25 scoring is negative (lower = more relevant); queries use bm25(applications_fts, 3.0, 2.0, 1.0, 1.0, 1.0) to weight company and title matches above notes. snippet() returns highlighted excerpts for result display.

Why it matters

This is the keystone. Without it, every other search idea — the MCP tool, the REST q param, the Cmd+K palette — is client-side filtering against a 200-record page rather than a real search. With it, every subsequent search feature is a 2-hour task layered on top of a working index. The three frames that converged on this idea independently (Leverage, Assumption-breaking, Cross-domain) all arrived at the same conclusion: FTS5 is what changes the architecture.

Basis
direct: server/db.js:14 — WAL mode confirmed. server/db.js:162–166 — extracted_jd column. server/db.js:110–141 — attachments.extracted_text. server/db.js:52–60 — stage_notes.content. server/db.js:169–184 — audit_log. No FTS virtual table anywhere in codebase.

external: SQLite FTS5 with external content tables avoids data duplication; INSERT/UPDATE/DELETE triggers maintain sync; snippet() returns highlighted excerpts; better-sqlite3 v12 supports FTS5 via db.exec().
Downsides
FTS5 triggers add write overhead — negligible at job-tracker scale (hundreds of records) but worth noting for large note fields. External content tables require discipline: if the source row is deleted without the trigger running (e.g., a raw SQL DELETE in tests), the index goes stale silently. BM25 scoring is negative (lower = more relevant), which is counterintuitive and needs a wrapper. One migration adds virtual tables + 6 triggers — test the migration rollback path.

search_applications MCP Tool + Unified q REST Param

Description

Add a search_applications MCP tool (tool #15) with a q text parameter that queries the FTS5 index and returns relevance-ranked results with snippet() match context — a different contract than list_applications (which enumerates and paginates). Simultaneously, add a q query parameter to the REST GET /api/applications route, passed through to svc.listApplications(). Both consumers hit the same underlying FTS5 query. Also fix the pre-existing bug: req.query.company_name is not currently forwarded from the REST route handler to the service (verified at routes/applications.js:54–59), despite the service supporting it — one-line fix, do it now regardless of which direction is chosen.

Why it matters

This idea had the highest cross-frame convergence: all 5 ideation frames identified it independently. AI agents using list_applications today must paginate through 200 records and scan locally to find anything — the MCP integration is a marketing feature, not a working one, for retrieval use cases. A dedicated search_applications tool with FTS5 backing changes the agent interaction from O(N) enumeration to O(1) intent expression. It also signals to the MCP contract that search and enumeration are different operations with different semantics, which prevents a messy parameter accumulation on list_applications.

Basis
direct: server/mcp.js:103 — "Use list_applications to locate records by ID, then call get_application(id) to fetch full detail" — documented N+1 workaround. server/mcp.js:116–131 — list_applications schema: status, company_name, updated_since only; no q. server/routes/applications.js:54–59 — req.query.company_name NOT passed to service (verified by verifier — live bug).

reasoned: Distinct tool contract signals intent: search_applications = find by relevance; list_applications = enumerate and paginate. Merging them via an extra param leads to parameter accumulation and semantic confusion for agent callers.
Downsides
Adding tool #15 increases the MCP surface (14 → 15 tools). The q param on REST adds a new query shape — existing clients are unaffected (param is optional), but the service layer needs the FTS5 query path alongside the existing WHERE-clause path. Relevance ranking means result ordering is non-deterministic for identical queries on changing data, which can confuse automated tests expecting stable ordering.

Full-Corpus Scope with FTS5 Snippets

Description

Scope the FTS5 index to cover all stored text — not just company_name and job_title, but also extracted_jd (full job description), stage_notes.content (per-stage interview notes), and attachments.extracted_text (CV and cover letter text). Return search results with snippet() highlighting that shows which passage matched — not just which record. A result for a search on "distributed systems" shows: [Acme Corp · Senior Engineer] → Stage: Interview → "…strong background in distributed systems and consensus protocols…" so the user never has to open the application to find the matching passage.

Why it matters

The most valuable text data the user generates is their own interview notes — salary numbers heard in a call, recruiter names, follow-up commitments. The most valuable pre-existing text is the full job description. Both are currently dark: stored in the DB, extracted at upload time, but retrievable only by opening each application individually. Making them searchable with snippet context turns a status board into a personal intelligence archive. A job seeker 3 months into a search can ask "which role mentioned equity cliff?" and get back the stage note that answered it.

Basis
direct: server/db.js:165 — extracted_jd TEXT; server/db.js:130 — attachments.extracted_text; server/db.js:56 — stage_notes.content TEXT NOT NULL. None referenced in any WHERE clause (grep-verified by basis verifier).

external: SQLite FTS5 snippet(table, col, open, close, ellipsis, tokens) — returns a highlighted excerpt fragment; standard for search result display.
Downsides
Large job descriptions (up to 10,000 chars per schema) and CV text increase FTS index size — still small at job-tracker scale but worth monitoring. Multiple FTS virtual tables (one per source table) require multiple triggers and possibly a JOIN to merge results ranked across tables. Stage note content can be sparsely filled (early-stage applications have no interview notes yet), so search results over stage_notes may return few hits for active pipelines.

Composable Filter Chips Replacing showClosed Toggle

Description

Replace the binary showClosed localStorage toggle with a composable chip bar. Each chip is a named, dismissible predicate: status:interview, status:offer, stale:>14d, has:cover-letter. Multiple chips combine as AND. Active chips appear in the toolbar as styled tags with a × close affordance. The existing per-stage design tokens (--stage-{name}-bg / --stage-{name}-fg in main.css) already style every stage chip — they need only an @click handler and a selectedStages reactive array. Fix the company_name REST route bug first (Idea 2 prerequisite) so filter predicates that hit the server actually work.

Why it matters

The entire current filter surface is one binary toggle. A job seeker with 40 applications across 7 stages who wants to focus on their 3 live interview processes must scan the full Kanban visually on every visit. The design token system for stage colors already exists and is applied to read-only status badges — adding clickable chip behavior is the highest-visibility, lowest-implementation-cost improvement in the search space. The verifier flagged the "afternoon" effort claim as optimistic (the REST bug is a prerequisite), but the concept and design language are fully grounded.

Basis
direct: client/src/App.vue:186,205–206 — SHOW_CLOSED_KEY is a binary localStorage boolean. client/src/assets/main.css:43–56 — per-stage color tokens (--stage-offer-bg, --stage-interview-fg, etc.) defined for every stage; currently applied only to read-only status badges.

external: Filter chip pattern (Linear, Jira) — validated prior art for dismissible predicate chips on tabular record sets.
Downsides
The company_name REST route bug is a prerequisite — server-side predicates silently fail until it's fixed. The Kanban view's Sortable.js constraint (KanbanBoard needs the full application array for drop zones, not a filtered one) means status-chip filtering may need to work differently for Kanban vs Table/Timeline — likely a prop for display-vs-drag separation. The "afternoon" estimate is optimistic; plan for a day including the REST fix and the Kanban/drag compatibility work.

Salary Range Filter with Data-Coverage Indicator

Description

Add salary_min_gte and salary_max_lte parameters to the service, REST route, and MCP list_applications tool. In the UI, expose as a salary range input in the filter chip bar (Idea 4). Critically: surface data coverage alongside the filter — "4 of 23 applications have salary recorded; showing 4 above £80k." The coverage count (COUNT(*) WHERE salary_min IS NOT NULL) is a single cheap aggregate. When the filter returns 0 results because salary data is absent, the coverage count explains why and makes the gap actionable ("6 applications you haven't recorded salary for yet").

Why it matters

Salary is the most decision-relevant field in an active job search — yet there is no way to filter by it today despite salary_min and salary_max being schema columns since a migration. The data-coverage indicator is the key insight: salary data is inherently sparse (many postings don't publish ranges), so a filter that silently returns empty results will be abandoned immediately. Showing "4 of 23 have salary recorded" transforms a broken-looking feature into a useful data-quality surface, and the prompt to fill gaps drives richer data for future filtering.

Basis
direct: server/db.js:93–97 — salary_min INTEGER, salary_max INTEGER columns added via migration. server/routes/applications.js:54–59 — salary params not present (verified). server/mcp.js:116–131 — list_applications schema has no salary filter.

reasoned: Salary data is sparse by nature; a filter returning 0 results silently is the failure mode. Coverage count (COUNT(*) WHERE salary_min IS NOT NULL) is a trivial aggregate that explains emptiness and drives data quality.
Downsides
Multi-currency salary data (the schema has a salary_currency column) makes range filtering across applications misleading — £80k and $80k are not comparable. The filter needs a currency selector or a "same currency only" caveat. Coverage counts add a second aggregation query to the list endpoint (one for the filtered results, one for coverage). Keep them as separate cheap counts, not joined, to avoid the double-scan anti-pattern documented in past learnings.

Change-Aware Search via Audit Log

Description

Expose the audit_log table as a searchable dimension: filter chips like action:status_changed since:7d or action:note_added since:interview. This is a different query shape from FTS5 full-text search — it searches the delta (what changed) rather than the snapshot (current state). Surfaces in the REST API as ?changed_action=status_changed&changed_since=7d and in the MCP as an optional parameter on list_applications. In the UI, a dedicated "What happened this week?" chip pre-populates with action:any since:7d.

Why it matters

The most urgent daily retrieval need for a job seeker isn't "find the record" but "what changed in my pipeline this week that I need to follow up on?" Today that answer requires scrolling the Timeline and mentally tracking changes. The audit_log already records every mutation — it's a write-only instrument with no read surface. Querying it gives a "recent activity" view without adding any new data collection, and the resulting filter ("applications where I added an interview note in the last 48 hours") is exactly the follow-up surface that turns the tracker into a daily workflow tool.

Basis
direct: server/db.js:169–184 — audit_log(application_id, user_email, action, source, auth_method, details, created_at) schema confirmed. No route, MCP tool, or service method exposes it for filtering (grep-verified).

reasoned: The delta query shape (what changed, not what is) is structurally different from FTS full-text and worth keeping as a separate filter dimension. Most useful as a "triage mode" entry point alongside keyword search.
Downsides
The details column is unstructured JSON — action types and their payload shapes are not formally documented, making the filter's vocabulary depend on what the write paths actually log. Audit log entries are never purged (no TTL), so over a long job search the log grows unbounded — a range-bounded query (always include a created_at > ? filter) is required to prevent full-table scans. Confidence is Medium (75%) because the action vocabulary and coverage need auditing before the filter's semantics can be trusted.

URL-Serialized Search State

Description

Serialize active filter state into URL query params (?status=interview,offer&q=distributed+systems&salary_min=80000) so any filtered view is bookmarkable, shareable, and survives a browser refresh. Currently all filter state lives in localStorage (SHOW_CLOSED_KEY) or component-local state — no Vue Router is installed. The minimal implementation uses history.replaceState() to push state changes without a router and reads params from new URLSearchParams(window.location.search) on mount. Admins sharing a filtered view of a user's pipeline with another admin becomes a URL copy-paste instead of a verbal description.

Why it matters

When search and filter chips land, filter state will be richer than a single localStorage boolean — restoring it on refresh will require either URL params or a more complex persistence mechanism. Building URL serialization now makes the foundation right before the feature complexity grows. It also enables a use case the current app doesn't support at all: sharing a specific view ("here's your active pipeline with salary filter applied") between users in a multi-user deployment.

Basis
direct: client/src/App.vue:169,186,206 — SHOW_CLOSED_KEY only filter state persisted; client/src/main.js — no Vue Router. client/src/components/TimelineView.vue:205 — separate localStorage sort key. No URL param reading anywhere in codebase.

reasoned: As filter dimensionality grows (status chips + q param + salary + date range), localStorage key proliferation becomes unmaintainable. URL params provide the same persistence with shareability and no key management overhead.
Downsides
Without Vue Router, URL param management is manual — history.replaceState() for writes, URLSearchParams for reads, no automatic route-to-component binding. Each new filter param must be explicitly serialized and deserialized. Adding Vue Router later would require migrating this manual state management. Medium complexity because the mechanics are straightforward but the coordination surface (every filter chip, every search input, every view toggle) is wide. The decision on Vue Router vs. manual URL state is worth surfacing explicitly before building.

Cluster A — Search as API layer

Sequencing note
