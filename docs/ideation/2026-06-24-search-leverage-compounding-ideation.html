1 FTS5 External Content Table as Canonical Search Layer
technical-approach Conf 90% Cx Medium

Add a SQLite FTS5 virtual table (applications_fts) using an external content table pointing at the real applications row, synced by AFTER INSERT/UPDATE/DELETE triggers. Index: company_name, role_title, job_description, interview_notes, prep_work, extracted_jd, plus an aggregated blob of stage_notes.content and attachments.extracted_text per application. Every future feature — the UI typeahead, MCP search tool, REST API, admin bulk queries — queries one surface with BM25 ranking, snippet() highlights, and boolean operators, rather than each writing its own LIKE soup.

Basis direct: server/db.js:69-72 — only two B-tree indexes; no FTS tables confirmed by verifier. server/db.js:128-140 — attachments.extracted_text stored but unsearchable. server/services/applications.js:119-143 — dynamic WHERE + LIKE is the entire search surface. external: SQLite FTS5 with better-sqlite3 v12 supports external content tables and synchronous triggers natively.
Rationale The FTS5 table is the investment that makes search correct and fast across every surface — UI typeahead, MCP tool, REST API, future admin dashboard — without duplicating logic. Without it, every surface writes diverging LIKE predicates. With it, a q=python+django parameter works identically for a human and an AI agent. The trigger-based sync means the index is never stale without a background job.
One-time schema migration required; external content table means DELETE must be handled carefully (FTS5 marks rows as deleted via a tombstone). Adding large text columns (stage_notes aggregation) modestly increases SQLite DB size.
We're building the search index once and everything — the UI, the AI agent, the admin view — queries it; do we commit to FTS5 as the foundation?
2 stage_notes FTS Aggregation Trigger
query-scope Conf 88% Cx Low

Add a trigger on stage_notes INSERT/UPDATE/DELETE that re-aggregates all note content for the parent application into the FTS5 index. A search for "negotiating equity" finds the application where that phrase appeared in an interview-stage note — no JOIN at query time, no explicit user action. Since the add_note MCP tool writes notes programmatically, any content an AI agent records is immediately searchable. This is the field most likely to surface applications a user would otherwise forget: notes are where the private signal lives.

Basis direct: server/db.js:52-60 — stage_notes(application_id, stage, content, created_at) with cascade delete confirmed by verifier. server/services/applications.js:37-46 — interview_notes 10,000-char limit confirms notes are substantive. mcp.js:437-475 — add_note MCP tool writes notes programmatically; indexing means agent-written content is immediately searchable.
Rationale Notes are where the job-search signal lives: "they mentioned a hiring freeze," "asked about relocation," "recruiter ghosted after offer stage." Without searchable notes, the tracker is write-only for anything more than company name. This makes stage_notes — currently a dark silo — a searchable knowledge base of the user's entire job search history, retroactively.
Aggregated notes blob grows with each note added; on very large note sets per application, the FTS5 row must be re-indexed on every note change. In practice (personal job tracker, <50 notes per application) this is negligible.
If notes were searchable, would the get_application_context MCP tool become less necessary — agents could find relevant applications by what's written in them rather than fetching full context for every application?
3 Dedicated search_applications MCP Tool
api-integration Conf 92% Cx Low

Add a purpose-specific search_applications tool to the MCP server alongside the existing 14 tools. It accepts q (freetext, runs against FTS5), filters (structured: status, salary_min, salary_max, location), limit, and offset. It returns {total, items, query_interpretation} — the query_interpretation field echoes back how the server parsed the query (fields searched, filters applied), so agents can verify they were understood without a second round-trip. Keeping it separate from list_applications preserves that tool's role as a reliable paginated enumerator.

Basis direct: mcp.js:102-201 — list_applications has only company_name (LIKE), status, updated_since; no content search confirmed by verifier. mcp.js:592-659 — get_application_context requires a known ID; agents have no find-by-content step. reasoned: Without a search tool, an agent asked "find the role where I mentioned Rust in my interview notes" must enumerate all 200 paginated records — expensive and fragile. A search tool makes retrieval compositional: search → get_application_context on the top match.
Rationale MCP integration is the differentiator of this tracker over simpler alternatives like JobSync. If the agent can't search by content, it degrades to a GUI replacement. With search_applications, every future agent workflow — "prep for tomorrow's interview," "find applications most similar to this offer," "what salary did I negotiate in comparable roles?" — becomes tractable without loading the full dataset.
Requires FTS5 foundation (Idea 1) to be meaningful beyond simple LIKE matching. query_interpretation response field adds implementation surface. Two tools with overlapping names may confuse less capable agents.
If an AI agent can call search_applications(query='backend rust interview') and get ranked results with snippets, what workflows does that unlock that don't exist today?
4 Push-Model Attention Surface Above Kanban
state-interaction Conf 88% Cx Low

A "Needs Attention" section — dismissible chips pinned above the Kanban board — dynamically populates with what the system already computes: stale applications past 14/30-day thresholds, deadline-approaching roles, salary mismatches against the user's compensation target. No query typed, no search initiated. The user opens the app and sees "3 stale applied roles — last touched 3 weeks ago" before they think to look for them. A parallel attentionApplications computed drawn from the same applications.value array in one pass avoids the double-scan performance trap documented in past learnings.

Basis direct: KanbanCard.vue:60-71 — STALE_STAGES and 14/30-day thresholds computed per card but never aggregated above the board; confirmed by verifier. server/db.js:207 — compensation_target_range on user_profiles; mismatch detection against salary_min/max on applications is a client-side computed with no API call. external: Filter chip pattern (Linear/Jira) — dismissible chips are a proven affordance for the design personality described ("tactical, forward, sharp").
Rationale Job seekers lose momentum on applications not because they forget the company name but because there is no forcing function to follow up. The app already knows the answer — it computes staleness per card — but buries it in color. Making the attention queue the first thing seen inverts search into delivery: the system surfaces what needs action before the user has to think to ask. This is also the highest-value interaction for episodic users who check in weekly rather than daily.
Chips above the board may feel noisy if many applications are simultaneously stale; requires dismissal state persisted to localStorage. Salary mismatch detection requires all applications to have salary data entered — partial data produces false negatives.
The card already turns orange when stale — why does the user have to find it instead of the board telling them what needs attention first?
5 Cmd+K Palette With Staleness-Preloaded Defaults
search-ux Conf 85% Cx Medium

A global Cmd+K / Ctrl+K command palette opens with the cursor ready but the list already populated — not blank. Default population is ordered by urgency: stale applications first, then recently updated, then by creation date. Typing narrows with client-side minisearch across company, role, location, and notes. The result cards show directly actionable affordances: "Open," "Add note," "View stage notes." Clicking a result calls the existing openPanel(app) flow without navigation. The palette is useful before the user types a single character because the system already knows what matters.

Basis direct: The search-ux evidence dossier confirms no Ctrl+K or Cmd+K shortcut exists in the application. App.vue:188-193 — full dataset already client-side; a minisearch index over 200 applications initializes in <10ms. App.vue:240-243 — openPanel(app) is the existing hook; palette results call it directly. external: minisearch noted as best client-side library for small datasets with field boosting. Linear command palette as prior art for action-returning search.
Rationale The design aesthetic ("tactical, forward, sharp — mission board meets editorial spread") is served by a keyboard-first command surface. A palette pre-populated with urgent applications compounds with the staleness computation already done — the user's most important next action appears the moment they open the palette, before they type. For technical self-hosted users, this is the dominant interaction model from their other tools (VS Code, Linear, Raycast).
minisearch adds a dependency (~15KB gzipped); client-side search over notes requires notes to be in the initial payload (they are, via the full dataset load). Palette must be accessible and keyboard-trapped correctly — implementation surface is non-trivial.
Every productivity tool our users already use has Cmd+K — the absence in a self-hosted tracker for technical users is immediately disorienting.
6 Salary + Location Structured Filter With Live Counts
query-scope Conf 90% Cx Low

Expose salary_min, salary_max, job_location, and salary_currency as first-class filter dimensions — a salary range slider plus location chips showing "3 of 47 match" before the user commits. These are numeric and categorical columns already in the schema; client-side filtering against the already-loaded dataset makes live counts zero-cost. A "remote AND >$130k" filter should show the survivor count before click. During offer negotiation, this turns the tracker from a status board into a compensation intelligence tool.

Basis direct: ApplicationPanel.vue:271-289 — salary_min/max rendered as number inputs; fields exist and are populated. server/db.js:91-107 — salary_min, salary_max, job_location, salary_currency confirmed as migration-added columns; verified by basis verifier. server/services/applications.js:103-122 — salary absent from current WHERE-clause construction; confirmed by verifier. App.vue:188-193 — full dataset client-side; live counts before commit require no API changes.
Rationale Salary and location are the fields users most need to compare across applications — they drive the withdrawal decision, the counter-offer decision, and the prioritization decision. Yet they are currently unsearchable and unfilterable. A salary range slider with live survivor counts answers "how many of my interviews led to sub-$120k offers?" — a question users cannot answer today without opening each card individually.
Salary data is only as useful as how consistently it's filled in — partial population produces misleading counts. Currency normalization across salary_currency values adds complexity if the user has multi-currency applications.
I can filter by company name but not by the $50k salary spread between my two offers — that's the wrong priority for a tool whose job is to help me make the right decision.
7 URL-Serialized Search State
state-interaction Conf 72% Cx Medium

Introduce a searchQuery ref in App.vue serialized to/from the URL query string (?q=…&status=interview&salary_min=120000). The URL becomes the canonical filter state: bookmarks, shared links, and browser back/forward restore the previous view exactly. For a multi-user self-hosted instance (admin + job-seeker pair), an admin can construct a pre-filtered URL ("your active interviews above $140k") and share it as a link rather than a verbal configuration session. The dragActive guard and panel-close watcher extend naturally since the new ref follows the same pattern as showClosed.

Basis direct: App.vue:186 — showClosed is a localStorage-backed ref; the URL-backed ref follows the same pattern but with wider reach. App.vue:203-207 — dragActive guard is the established mutation guard; any new filter ref extends it. App.vue:216-224 — panel-close watcher is the established template for "filter changed → check if panel app is still visible." SettingsPanel.vue:450-467 — showAllUsers admin toggle confirms multi-user dimension exists. reasoned: URL-encoding filter state requires only router integration — no server storage; the filter grammar (Idea 4 DSL or structured params) maps directly to URL params.
Rationale The URL is a multiplier: bookmarks, shared links, back-button navigation, and agent-generated deep links in generated documents all become possible once filter state lives in the URL. An MCP-generated report can include a link to "your pipeline as of today" that opens the filtered view. This is the cheapest path to saved filter views — store the URL, not a named view object in the database.
Vue Router integration is a contained but non-trivial refactor if the app doesn't already use hash-mode routing; URL length limits apply to very long query strings. Lower confidence than other ideas because URL persistence is currently inferred rather than directly evidenced in the codebase — depends on router setup.
If filter state lived in the URL, would the back button and shareable links alone justify the router refactor — and could MCP-generated documents link to pre-filtered board views?
Rejection Summary

Rejection Summary

Idea Reason Rejected
Unified q= Param Propagation (Candidate 3) Verifier found the "single choke point" claim overstated — route and client method both need changes, not just the service; subsumed by FTS5 foundation + MCP tool together which are more precise about what changes where.
Structured Filter DSL (mini-grammar) ~80-line parser is a maintenance surface for a personal tool; filter chips + structured params (Ideas 4, 5, 6) achieve 90% of value with no grammar to maintain. Better as a brainstorm follow-on if the UX matures.
Deadline + Staleness Search Ranking Deadline column presence in migrations not cleanly verified; compositing BM25 score with staleness signal is non-trivial (requires score normalization). Staleness surfacing via attention chips (Idea 4) is simpler and more direct.
Pathologist's Differential Funnel Progressive elimination funnel adds significant UX complexity over filter chips with no demonstrated gap the chips don't cover; interaction model conflicts with the direct action palette (Idea 5).
Music Key Signature Search Context The "context" abstraction (implicit scope applied to subsequent queries) adds cognitive load for solo users; URL state (Idea 7) is a simpler implementation of the same persistence intent.
Archaeological Stratigraphy (Phase Labels) Phase-labeled match snippets are a nice UX detail but not load-bearing; FTS5 snippet() already surfaces the matched text and the stage_notes.stage column provides the label — this is an incremental display refinement, not a distinct architecture.
Profile Fit Score (Inverse Match) Sound idea but crosses from search into recommendation system; scoring rubric (keyword match vs. semantic similarity) is underdefined and requires either LLM call or heuristic. Lower implementation confidence than salary/location filter which uses raw numeric data.
Extracted JD Skills Tag Cloud Contingent on extract_job_description having been run per application — adoption must be near-universal for the tag cloud to be meaningful. Salary + location filter (Idea 6) uses raw numeric data that doesn't depend on a prior MCP call having been executed.
Audit-Log Time-Range Query Niche use case (reviewing job search by week of activity); requires new UI component on Timeline; lower value density versus other search surfaces where the same implementation effort yields higher daily utility.
Attention Digest Push (Morning Report) Interesting inversion (push vs. pull) but introduces server-side cron or external delivery mechanism — complexity outside the current Docker single-image architecture. The push-model chips (Idea 4) achieve the same "system surfaces attention" goal entirely client-side.
Search Returns Actions Only (No Records) Action-card results are a UX pattern atop regular search, not an alternative architecture; the Cmd+K palette (Idea 5) can include action affordances per result card — no need to drop record display entirely.
Timeline Scrubbing Interface Temporal range queries are genuinely useful but the scrubber is a new UI component that lives in the Timeline view specifically — better scoped to a Timeline enhancement than to the primary search frame. Lower axis coverage value given other search-ux survivors.
