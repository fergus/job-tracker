Grounding Context
Stack
Vue 3 + Express 5, SQLite WAL (better-sqlite3 v12.11.1), Docker single-image, oauth2-proxy. No state manager — flat applications ref in App.vue.
Current Search State
No text search exists. Only filters: status (showClosed toggle), updated_since, company_name LIKE — but company_name is silently dropped by the REST route handler despite the service supporting it.
Rich Unsearchable Fields
job_description, extracted_jd (JSON), stage_notes.content, attachments.extracted_text, notes, contact_name — none indexed or filterable.
MCP Layer
14 tools on port 3001. list_applications accepts status + company_name only. MCP docs explicitly describe a two-step retrieve-then-fetch pattern for rich-text queries.
Key Learnings
Double-array-scan risk (use single combined pass). dragActive guard required for filter mutations. Panel close must be synchronous (not nextTick) when filter removes visible application.
Competitive Gap
No job tracker competitor (Huntr, Teal, Simplify, JobSync) implements saved filter views, FTS across notes/attachments, or search-as-navigation — open differentiation space.

1. technical-approach High confidence Large

FTS5 Universal Search Substrate

Build a SQLite FTS5 external content table spanning company_name, job_title, job_description, notes, extracted_jd text, and — via a join — stage_notes.content and attachments.extracted_text. This single schema change becomes the substrate every other search idea plugs into: ranked results, snippet highlighting, cross-field queries, and future field additions all become a WHERE clause against the FTS table rather than a new indexing strategy. Use the trigram tokenizer for substring match at negligible cost for 200 records.

Basis direct "No full-text index or LIKE optimization" and "extracted_text stores OCR/parsed content; no index or search on it" — evidence-technical-approach.md:154, :200. RETURNING clause incompatibility with FTS5 triggers documented in grounding (fetch lastInsertRowid separately).
Rationale Every subsequent search feature becomes a WHERE clause against the FTS table rather than a new indexing strategy. Building this first means the cost of each next search idea drops from a multi-day task to hours. It also makes the MCP list_applications tool genuinely useful for rich-text queries that currently require N round-trips.
Downsides Three triggers required per table (INSERT, DELETE, UPDATE with correct delete-before-update order). RETURNING clauses must be removed from write paths (fetch lastInsertRowid separately). One-time migration cost. Trigram tokenizer creates a larger index than unicode61, but negligible at 200 records.
"We built one index that makes every search feature from here out a 2-hour task instead of a 2-day task."
2. query-scope High confidence Medium Frame B: Constraint-flip

Full-Corpus Query Scope

Constraint flip: what if there were no unsearchable text in the database? Index every text field — stage_notes.content, extracted_jd, attachments.extracted_text, notes, job_description — into the FTS5 substrate. When a query matches inside a note or attachment, the parent application surfaces in results with a snippet indicating which sub-document matched ("found in: interview note, 14 days ago"). This inverts the current pattern where the richest content in the system — what the user personally wrote about each company — is entirely dark to search.

Basis direct "Stage_notes content NOT in WHERE clause — joined only when includeNotes=true" (evidence-query-scope.md:56). direct "Attachment extracted_text only returned in get_application_context" (evidence-query-scope.md:85). The MCP guidance explicitly documents the limitation: "Use list_applications to locate records by ID, then call get_application(id) to fetch full detail including extracted_jd, interview_notes."
Rationale Interview notes are the highest-signal text in the tracker — they record what was said, what impressed, what was concerning. Locking them out of search means the most contextually rich content the user personally wrote can never be found by content. A job seeker who wrote "mentioned stock options" or "lowball offer" three weeks ago cannot retrieve that application without scrolling the whole board.
Downsides Stage notes are in a separate table — the FTS trigger must join across tables or duplicate the content into the FTS index. Attachment text can be long (PDFs); snippet() truncation needed. Cross-table FTS5 external content requires careful design of the virtual table schema.
"I remember interviewing somewhere that asked about distributed tracing — that should just work."
3. api-integration High confidence Medium Frame B: Constraint-flip

search_applications MCP Tool + Unified q REST Param

Two changes that form one coherent contract: (1) add a single q string parameter to GET /api/applications that queries the FTS5 substrate across all text fields, returning ranked results with snippet per match; (2) add a dedicated search_applications MCP tool that accepts q and returns results with score and snippet fields, distinct from list_applications. Also: fix the one-line bug where req.query.company_name is silently dropped at the route handler despite the service correctly handling it — both the browser client and MCP already handle it, only the REST route is broken.

Basis direct MCP docs explicitly document the two-step limitation: "Use list_applications to locate records by ID, then call get_application(id) to fetch full detail including extracted_jd, interview_notes" (evidence-query-scope.md:27). direct "req.query.company_name NOT passed to service, despite service supporting it" (evidence-technical-approach.md:221) — one-line bug fix bundled here.
Rationale A dedicated search tool with ranked results and snippets makes the MCP layer genuinely useful for rich-text lookups. Once agents learn to call search_applications, every improvement to the underlying index (stage notes, attachment text) makes every agent workflow better without prompt changes. The snippet return lets agents reason about relevance without fetching full records, reducing token usage.
Downsides Requires Idea 1 (FTS5 substrate) as a prerequisite. Adds a new MCP tool that AI clients need to learn about. REST versioning: existing clients using GET /api/applications unaffected (new q param is optional), but the search response shape may need a new content-type or field for snippets.
"An AI agent asked 'which roles mentioned equity compensation' should answer in one tool call, not twenty."
4. search-ux High confidence Medium Frame A: Assumption-break

Command Palette (Cmd+K) — Search as Navigation

Assumption broken: search and navigation are different affordances. A Cmd+K command palette unifies find-record and perform-action into one keyboard-triggered surface. Typing "Stripe" finds the application and opens its panel. Typing "interview" activates a stage filter. Typing a company name opens the panel directly — no mouse, no board scanning, no column hunting. Operates client-side on the in-memory applications array using MiniSearch (radix-tree prefix, field boosting, fuzzy tolerance) — zero server round-trips, instant results. Consistent with the "tactical, forward, sharp" design aesthetic.

Basis direct "No global search/filter hotkeys documented" (evidence-search-ux.md:43). Cards have Enter/Space for selection but no global search entry point. external Linear Cmd+K and Notion Cmd+P — the converging pattern in productivity tools for power users who reach for keyboard-first interfaces. MiniSearch: zero dependencies, 3.7M weekly downloads, JSON-serializable index for localStorage caching.
Rationale Self-hosted technical users have high keyboard fluency. The command palette maps exactly to the "mission board meets editorial spread" aesthetic — operators navigate by command, not by scroll. A palette also creates a natural home for richer filter input without cluttering the toolbar, and the MiniSearch radix tree enables prefix search (type "Str" → Stripe, Stripe 2) at zero server cost.
Downsides Client-side search scope limited to fields loaded in the applications list (not stage_notes or attachment text without API changes). Requires a new Vue component. Drag-active guard must apply: palette should not trigger filter mutations while dragActive is true. Does not replace server-side FTS for full-text — complementary, not a substitute.
"Cmd+K → company name → opens application panel — without touching the mouse from any view."
5. state-interaction High confidence Medium

Composable Filter Chips — Replace the Binary showClosed Toggle

The current filter system is a single binary toggle (showClosed) with no composition. Replace it with a filter chip model: active filters appear as dismissible chips in the toolbar (status, salary band, location, date range). Each chip is an orthogonal dimension composing with AND across dimensions. The dragActive guard pattern already exists at toggleShowClosed() — new filter mutations follow the same guard. The existing panel-close watcher pattern (watch(showClosed, ...)) extends directly to close the panel synchronously when any filter removes the visible application from the result set.

Basis direct "Single toggle only: Binary showClosed state controlling column visibility" (evidence-search-ux.md:88). direct "function toggleShowClosed() { if (dragActive.value) return; }" (evidence-state-interaction.md:31) — guard pattern already established, new chip mutations follow the same pattern. external Linear filter chip pattern: AND across dimensions, OR within; dismissible chips in toolbar.
Rationale A user cannot currently say "show me everything in interview stage with salary above £100k." Every structured data field — salary, location, deadline, applied_at — sits in the database unused at filter time. The composable chip model is architecturally cleaner than bolting additional toggles onto the current binary model, and it extends to text search (a text query becomes another chip).
Downsides Replacing showClosed requires migrating existing localStorage preference key. Panel-close watcher must be updated to react to the new multi-dimensional filter predicate rather than just the binary closed state. The combined displayApplications + count computed must use a single-pass pattern (per documented learnings) to avoid double array scan performance issues.
"Replacing showClosed with a filter chip system is architecturally cleaner than adding more toggles — and it opens every dimension we've been ignoring."
6. search-ux Med confidence Medium Frame A: Assumption-break

Active-Context "Hot Board" — Data Interfaces to the User

Deepest assumption broken: search is about finding records the user already knows exist. Reframe: data interfaces to the user. A computed urgency filter surfaces applications by signal rather than text query — deadline within 7 days, status stuck in the same stage for 14+ days, priority=high with no updated_at change in 5 days. This is a predefined compound filter expressed as a single-click mode: "Show me what needs attention right now." The Hot Board view becomes the default on returning visits, not Kanban. No text input required.

Basis direct "All date transition fields exist (no range queries): interested_at, applied_at, responded_at, interview_at, offer_at, closed_at" (evidence-query-scope.md:104–106). direct watch(showClosed, (visible) => { if (!visible && panelApp.value && TERMINAL_STAGES.includes(...)) { showPanel.value = false; } }) (evidence-state-interaction.md:52–63) — the panel-close watcher pattern is directly reusable for urgency-driven filter changes. direct "KanbanBoard receives raw applications (unfiltered)" — urgency filter belongs at App.vue level like showClosed.
Rationale Most job tracker abandonment happens not from poor data entry but from loss of situational awareness. A filter that presents the tracker's own read of "here's what matters today" inverts the relationship between user and data — it matches the mission-board design intent. Monday morning opens and the three applications that have gone stale are surfaced without any typing.
Downsides Medium confidence: urgency signals need tuning (what counts as "stuck"?). Needs user preference to set as default vs opt-in mode. "Stuck 14 days" needs to be configurable. The deadline field is not always populated — users who don't fill it won't see deadline signals. Requires careful UX to communicate why an application is surfaced.
"Opening the tracker on Monday shows the three applications that need action — without typing anything."
7. api-integration Med confidence Small

Salary + Date Range API Params

Add salary_min_gte, salary_max_lte, deadline_before, and location parameters to both GET /api/applications and the list_applications MCP tool. The service layer's dynamic WHERE clause builder already supports this pattern (it already adds conditions for status, updated_since, and company_name). These are numeric range and equality comparisons — no FTS required. Salary range filtering is independently valuable even without full-text search: "show me everything where the offered max is above £150k" is a 4-line addition to the service.

Basis direct "salary_min INTEGER, salary_max INTEGER" added via migration (evidence-query-scope.md:96–97). direct "Suggested summary preset: [...'salary_min', 'salary_max'...]" (evidence-query-scope.md:110) — fields already treated as query-relevant in MCP context but not filterable. direct The WHERE clause builder pattern at service lines 95–125 shows exactly where these conditions append (evidence-technical-approach.md:13–35).
Rationale Salary is among the top two reasons a job seeker accepts or declines. Having it in the schema but not filterable means users scan every card manually when evaluating a pipeline. This is a small addition (4–6 service lines, minimal schema cost) that delivers immediate value. It also makes the MCP layer useful for AI prompts like "show me all interviews offering above $180k."
Downsides Salary data is sparsely populated (users don't always fill it). Range queries on NULL values need careful handling (salary_min IS NULL OR salary_min >= ? vs strict). Medium confidence because value depends on how consistently users populate salary fields. Independently shippable without FTS substrate.
"Show me all applications where the offered max is above £150k — one filter, no scrolling."
